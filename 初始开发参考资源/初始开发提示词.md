# Markdown 转 Word / PDF 桌面程序开发提示词（C# + WinUI 3 版）

> 提示词版本：v2.0（C# + WinUI 3）
>
> 项目定位：Windows 10/11 离线运行的现代化 Markdown 文档转换桌面程序
>
> 开发方式：VibeCoding（将本文件作为 OpenCode、Codex、Claude Code、Trae 等 AI 编程工具的项目总提示词与单一事实来源）

---

## 1. 项目概述

### 1.1 项目名称

暂定名称：**Markdown Document Converter**。产品名可在开发阶段调整，但不得影响命名空间、应用标识和资源管理的清晰性。

### 1.2 项目目标

开发一款面向 Windows 10/11 的现代化桌面 GUI 程序，将 Markdown 文档转换为 Microsoft Word `.docx` 与 PDF `.pdf`。

硬性要求：

- 使用 **C# + WinUI 3 + Windows App SDK** 开发，不使用 Python、PySide6、WPF、WinForms、Electron 或 WebView 作为主界面框架。
- 使用 XAML 构建真正的 WinUI 3 界面，遵循 Fluent Design，现代、美观、响应式，并支持键盘操作和高 DPI。
- 完全离线运行：转换时不访问互联网，不上传文档，不下载字体/公式/资源，不调用在线转换服务。
- 支持单文件、多选文件、拖放文件、文件夹递归扫描和批量转换。
- Word 与 PDF 采用两条独立转换链，均直接从 Markdown 源文件生成。
- 支持 A4/A5；提供现代文档、学术、简约等内置样式；禁止用户导入自己的 Word 模板。
- 支持中文排版、常用 Markdown 扩展、数学公式、YAML Front Matter、目录、书签、页码、页眉页脚、超链接、脚注和代码块。
- Word 数学公式必须输出为可继续编辑的 Word 原生公式对象（OMML），禁止默认转成公式截图；PDF 数学公式必须正常排版。
- 用户可选择系统已安装字体，并可统一调整整体字号比例；不允许逐个修改标题、正文、代码等不同层级的字号。
- 支持配置保存、跟随 Windows 浅色/深色主题、日志、错误提示、取消任务、失败任务重试、转换完成后打开输出目录。
- 最终交付 Windows 安装包，目标机不需要用户自行安装 .NET、Windows App SDK、Pandoc 或 Typst；所有必需的运行时和转换工具均随安装包提供。

建议开发基线：使用当前受支持的 **.NET 10 LTS / C# 14**，并选择开发开始时 Windows App SDK 的最新稳定版本。版本必须在项目文件中固定，禁止使用 Preview/Experimental 依赖。若实际 WinUI 3 项目模板或目标环境对版本有兼容限制，应先做最小验证，再锁定一个受支持的稳定版本并记录原因。

### 1.3 核心原则

1. **本地优先**：用户文档及元数据不得离开本机。
2. **转换链独立**：Word 和 PDF 分别从 Markdown 源文件独立生成。
3. **转换引擎与 UI 解耦**：XAML 页面只负责交互和展示，转换服务不得依赖具体 View。
4. **原生 WinUI 3**：用 NavigationView、CommandBar、InfoBar、ProgressBar、TeachingTip（仅在确有帮助时）等原生控件构建界面，不使用浏览器技术仿制桌面 UI。
5. **内置样式优先**：程序提供固定的内置样式，不开放外部模板导入。
6. **全局排版控制**：字体可选择、字号只允许统一缩放，保持不同文档样式内部比例一致。
7. **依赖精简**：只加入实现明确需求所必需的 NuGet 包，优先使用 .NET、Windows App SDK 和 BCL 自带能力。
8. **可验证的 VibeCoding**：AI 必须分阶段实现，每阶段生成可运行代码、执行构建和测试，并在 README 记录实际命令与结果。

## 3. 输出能力

## 3.1 Word

输出：`.docx`

Word 输出必须具备：

- 可编辑文本
- 标题样式
- Word 导航窗格可识别标题层级
- 自动目录
- 页眉
- 页脚
- 页码
- 超链接
- 脚注
- 表格
- 代码块
- 数学公式对象
- 中文字体设置
- 页边距
- A4/A5 页面
- 内置样式套用

数学公式必须优先生成 Word 原生 OMML 数学标记，禁止将公式渲染成 PNG/JPG 作为默认实现。

Pandoc 对 DOCX 的数学输出使用 OMML，因此可以满足 Word 中继续编辑公式的目标。

## 3.2 PDF

输出：`.pdf`

PDF 输出必须具备：

- A4
- A5
- 自动目录
- PDF 书签
- 页码
- 页眉
- 页脚
- 超链接
- 脚注
- 可搜索文本
- 正常数学排版
- 中文字体嵌入/正确选择
- 稳定的分页
- 标题层级
- 表格分页

PDF 不通过“Markdown → Word → PDF”生成，而是单独执行 PDF 转换链。

推荐链路：

```text
Markdown
   ↓
Pandoc AST / Pandoc Markdown
   ↓
Typst
   ↓
PDF
```

Typst 原生以 PDF 为主要输出，并支持 PDF outline/bookmark 等结构化能力；Pandoc 当前也提供 Typst PDF engine 集成，因此适合本项目的离线 PDF 管线。

## 4.2 技术选型

### 应用与界面

- C#、当前受支持的 .NET LTS、C# 语言版本跟随该 SDK 的稳定版本。
- WinUI 3 + Windows App SDK，使用 XAML 和标准 WinUI 控件。
- MVVM 分层；ViewModel 实现 `INotifyPropertyChanged`，命令使用清晰、可测试的 `ICommand` 实现。
- 默认不引入 CommunityToolkit.Mvvm、ReactiveUI 或大型 UI 控件库。若 AI 认为某个 NuGet 包不可替代，必须先说明需求、维护状态、许可证和体积影响，并将其纳入依赖清单。
- 不使用 WPF、WinForms、Qt、WebView/HTML 或自绘整套控件替代 WinUI 3。

### Markdown 与文档转换

- Pandoc：解析 Markdown、输出 DOCX、输出 Typst 源码。
- Typst：编译 Typst 源码为 PDF。
- Word 使用 Pandoc 的 DOCX 输出和 OMML 数学公式支持。
- PDF 通过 Pandoc→Typst 独立生成，不允许先转成 DOCX 再转 PDF。
- 将 Pandoc 和 Typst 的 Windows 可执行文件作为应用私有资源随安装包发布，并固定已验证的版本和 SHA-256 校验值；不得在首次启动时联网下载。

### 运行时进程调用

使用 `System.Diagnostics.Process`，通过 `ProcessStartInfo.ArgumentList` 逐项添加参数，设置 `UseShellExecute = false`，异步读取标准输出与标准错误，并使用 `WaitForExitAsync(CancellationToken)` 等待。

严禁拼接 shell 命令、严禁依赖 `cmd.exe`/PowerShell 执行转换命令、严禁以 `UseShellExecute = true` 调用引擎。输入路径、输出路径和元数据需按参数独立传递；不要把用户内容写入临时脚本后执行，除非该引擎明确要求且已进行必要转义。

### 配置、序列化与日志

- 使用 `System.Text.Json` 读写设置。
- 配置文件采用 UTF-8，带 `config_version`，可迁移旧版本配置。
- 使用 `Microsoft.Extensions.Logging` 或轻量的应用内日志抽象；不要把业务日志直接写入 UI 控件。
- 用户配置保存在 `%APPDATA%/MarkdownDocumentConverter/`。

### 测试与安装

- 单元测试优先使用 xUnit；只有在与测试目标不匹配时才考虑其他测试框架。
- 安装包使用 Inno Setup 包装自包含的 WinUI 3 发布目录、Pandoc、Typst、样式与元数据资源。
- 目标机离线安装后可直接启动；不得要求用户预装 .NET SDK、.NET Runtime、Windows App SDK Runtime、Pandoc 或 Typst。

WinUI 3 是 Microsoft 推荐的新 Windows 桌面 UI 框架；.NET 10 是 LTS 版本。具体版本以开发时稳定版官方文档为准：
- [WinUI 3 官方文档](https://learn.microsoft.com/windows/apps/winui)
- [.NET 10 新增功能与支持周期](https://learn.microsoft.com/dotnet/core/whats-new/dotnet-10/overview)
- [Windows App SDK 自包含部署](https://learn.microsoft.com/windows/apps/package-and-deploy/unpackage-winui-app)

- 保留中间文件（默认关闭）

普通用户界面不主动暴露这些高级选项。

## 7. WinUI 3 / Fluent Design 视觉规范

必须使用真正的 WinUI 3 控件与 XAML ResourceDictionary，不是“模仿 WinUI 的其他 GUI”。

### 7.1 设计元素

- 采用 Windows 11 Fluent Design 视觉语言：清晰的层级、适当留白、分组卡片、合理圆角、系统强调色、细腻但不过度的动效。
- 主体用 `NavigationView` 构建“转换 / 设置”导航；主要操作优先放在清晰的页面操作区。
- 使用 WinUI 3 原生 `Button`、`ComboBox`、`CheckBox`、`ProgressBar`、`ProgressRing`、`InfoBar`、`ContentDialog`、`TeachingTip` 等控件；仅在确有必要时自定义模板。
- 正确处理 Hover、Pressed、Disabled、FocusVisual、选中和错误状态。
- 适配 100% 至 200% 及更高 DPI；窗口缩放时布局不能重叠或裁切。
- 主窗口应能在常见笔记本屏幕下舒适使用；窗口窄时布局应合理折叠，不要简单把所有控件挤在一行。
- 避免大面积纯色渐变、过度透明、复杂背景和装饰性动画影响文档工具的效率。

### 7.2 主题

默认跟随 Windows 系统主题。不要把 `RequestedTheme` 固定为 Light 或 Dark；除非用户明确选择，否则应使用系统默认主题行为。

必须保证：

- 浅色与深色主题的背景、文本、边框、图标、状态色都有足够对比度。
- 主题变化时控件资源正确更新。
- Focus 状态明显、键盘导航顺序合理。
- 尊重减少动态效果等系统可访问性偏好（在 WinUI 3 可用 API 范围内）。
- 文案使用简体中文为主；资源组织方式应允许以后增加语言，不要求首版完成多语言界面。

## 8. Markdown 解析与预处理

## 8.1 解析策略

不要自行实现完整 Markdown Parser。主解析与转换逻辑交给 Pandoc，C# Core 层负责：

1. 校验输入文件、扩展名和读写权限。
2. 读取或检查 YAML Front Matter（如业务需要元数据模型，优先通过 Pandoc JSON AST 获取解析结果，避免自行实现不完整的 YAML 解析器）。
3. 合并用户选择的页面尺寸、内置样式、字体和全局字号比例。
4. 构造参数列表，不拼接 shell 字符串。
5. 调用对应的 Pandoc / Typst 可执行文件。
6. 捕获输出、处理取消/超时、映射用户友好的错误。
7. 校验生成文件存在且有效，记录日志与耗时。

C# 业务层不要尝试把所有 Markdown 转换为自己的内部文档模型；除必要的元数据和校验外，应尊重 Pandoc 的解析结果。

## 8.2 Front Matter

例如：

```yaml
---
title: Markdown 文档示例
author: 示例作者
date: 2026-09-25
subject: 文档转换测试
keywords:
  - Markdown
  - Word
  - PDF
lang: zh-CN
---
```

| Markdown 元数据 | Word | PDF |
|---|---|---|
| `title` | 文档标题/标题页 | 文档标题 |
| `author` | 作者属性/标题页 | 作者信息 |
| `date` | 日期 | 日期 |
| `subject` | 文档主题 | PDF 元数据 |
| `keywords` | 关键词属性 | PDF 元数据 |

## 9.1 内置样式

### 现代文档

用途：日常文档、说明文档、项目文档。清晰的标题层级、适度段间距、现代感、代码块易读、表格简洁。

## 16. 并发与任务系统

UI 线程不得直接运行 Pandoc/Typst，也不得同步等待子进程退出。

使用基于 `Task`、`async/await`、`CancellationToken` 和 `SemaphoreSlim` 的异步任务系统：

```text
ConvertViewModel
      │ Start / Cancel / Retry
      ▼
BatchService
      │ SemaphoreSlim（限制并发）
      ▼
ConversionCoordinator
      ├── WordPipeline ── ProcessRunner ── Pandoc
      └── PdfPipeline  ── ProcessRunner ── Pandoc → Typst

Progress / Result / Error
      └── IProgress<T> 或线程安全事件 → ViewModel → XAML Binding
```

要求：

- 默认并发数为 1；高级设置可提高并发数，但必须设合理上限。
- UI 状态更新必须回到 UI Dispatcher；Core 层不直接访问 Dispatcher。
- 每个文件及每条输出管线有独立任务状态，可分别显示 Word/PDF 成功或失败。
- 取消任务时传递 `CancellationToken`，同时尝试终止对应的 Pandoc/Typst 进程及其子进程，不能只停止界面上的进度显示。
- 单文件失败不得中断整个批次。
- 任务状态包含 `Waiting`、`Running`、`Success`、`Failed`、`Cancelled`、`Skipped`。
- 释放 `Process`、`CancellationTokenSource`、临时目录和日志句柄；防止事件订阅造成内存泄漏。
- 不为简单的 CLI 封装过度引入复杂后台服务框架。

## 17. 子进程管理

使用统一 `ProcessRunner` 封装所有外部工具调用。示意代码：

```csharp
var startInfo = new ProcessStartInfo
{
    FileName = executablePath,
    WorkingDirectory = workingDirectory,
    UseShellExecute = false,
    RedirectStandardOutput = true,
    RedirectStandardError = true,
    CreateNoWindow = true
};

foreach (var argument in arguments)
{
    startInfo.ArgumentList.Add(argument);
}

using var process = new Process { StartInfo = startInfo };
process.Start();

var stdoutTask = process.StandardOutput.ReadToEndAsync(cancellationToken);
var stderrTask = process.StandardError.ReadToEndAsync(cancellationToken);
await process.WaitForExitAsync(cancellationToken);
var stdout = await stdoutTask;
var stderr = await stderrTask;
```

上面是说明调用方式的示意代码，实际实现必须处理超时、取消、进程启动失败、输出流并行读取、退出码、进程树终止与资源清理。针对不同目标框架验证 `ReadToEndAsync`、`WaitForExitAsync` 重载是否可用，不可凭空假定 API。

必须：

- 使用 `ProcessStartInfo.ArgumentList`，禁止手工拼接命令行。
- 设置 `UseShellExecute = false`，不得调用 shell 执行命令。
- 同时异步读取 stdout/stderr，避免缓冲区写满导致死锁。
- 为每个引擎设置可配置超时。
- 支持取消并尽可能终止进程树。
- 收集退出码、运行时间与必要的错误上下文。
- 将原始 stderr 保留在技术日志中，并把错误摘要转换为用户可理解的简体中文。
- 不把敏感的 Markdown 正文完整写入日志；默认记录文件名和路径，并允许用户查看详细日志。

## 28. VibeCoding 开发规则

本项目严禁一次性生成整个应用后再集中修复。必须按可验证的小步推进，并持续保持程序可构建、可运行。

### 28.1 项目总提示词

将以下规则作为 AI 编程工具的长期项目指令：

```text
你正在开发一个 Windows 10/11 的 Markdown 转 Word/PDF 桌面程序。
技术栈固定为 C# + WinUI 3 + Windows App SDK；不要改成 Python/PySide6、WPF、WinForms、Electron 或 Web 应用。
目标为当前受支持的 .NET LTS（建议 .NET 10 LTS）与 Windows App SDK 稳定版本；先验证本机工具链，再锁定 SDK/包版本。不得使用 Preview/Experimental 包。

核心硬性要求：
1. 使用真正的 WinUI 3 XAML 与 Fluent Design；不使用 WebView/HTML 冒充原生 UI。
2. UI 与核心业务分层；Core 项目不能引用 WinUI 类型。
3. 使用 MVVM；View 不实现复杂业务逻辑，ViewModel 不直接启动外部进程。
4. 不在 UI 线程同步等待 Pandoc/Typst；使用 async/await、CancellationToken 和异步进程输出读取。
5. 通过 ProcessStartInfo.ArgumentList 传参，UseShellExecute=false；禁止 shell 命令拼接、禁止 cmd/PowerShell 包装执行。
6. Word 与 PDF 必须独立生成：Markdown→Pandoc→DOCX；Markdown→Pandoc→Typst→PDF。
7. Word 数学公式必须是 OMML 原生公式对象，禁止公式截图作为默认实现。
8. 首版不支持图片输入，不添加图片处理/网络图片抓取功能。
9. 程序必须完全离线，不添加分析统计、更新检查、遥测、账号、云同步或联网下载。
10. 只允许内置的普通/现代文档、学术、简约样式，不提供用户导入 Word 模板的入口。
11. 用户可以选择系统字体与全局字号比例，但不得增加各级标题、正文、代码等独立字号滑块。
12. 所有引擎、模板、图标和元数据资源由 ResourceLocator 统一定位，不得硬编码开发机绝对路径。
13. 所有外部进程必须捕获 stdout/stderr、记录退出码，支持超时、取消、进程树终止和资源清理。
14. 单个文件失败不得中断整个批次；状态和错误信息要能按文件/输出格式区分。
15. 配置使用 System.Text.Json；路径处理使用 System.IO 的 Path/Directory API；时区/文化格式不得依赖开发机默认值。
16. 不增加没有明确收益的 NuGet 包；新增依赖前核对官方文档、版本、许可证、维护状态和体积。
17. 修改文件前先阅读相关 ViewModel、服务、模型和测试；避免与需求无关的大规模重构。
18. 每次修改后运行 dotnet build 和受影响的测试。修复全部警告或解释为什么某个警告可接受。
19. 所有用户可见错误经过统一错误模型转换，消息使用清晰简体中文；技术细节写入日志。
20. 不凭训练数据猜 API。遇到不确定的 WinUI/.NET/Windows App SDK API 时，先查当前版本官方文档或示例，再实现。
21. 不把真实用户文档写入测试日志；不覆盖源 Markdown；输出冲突遵循配置策略。
22. 先交付最小可运行闭环，再逐步完成批处理、设置、样式、测试和安装包。
23. 发布必须在干净的 Windows 10/11 测试环境中验证，安装后不要求用户预装 SDK、运行时、Pandoc 或 Typst。
```

### 28.2 每次让 AI 执行任务时的工作方式

每次提示 AI 完成一个阶段或任务时，要求它：

## 33. 最终产品定义

最终产品应是一款：

> **Windows 原生感较强、离线运行、操作简单、排版稳定的 Markdown 专业转换工具。**

用户的典型操作应压缩为：

```text
拖入 Markdown
       ↓
选择 Word / PDF
       ↓
选择风格
       ↓
点击转换
       ↓
获得专业排版文档
```

核心技术结构：

```text
                    Markdown
                        │
                 ┌──────┴──────┐
                 │  Preprocess │
                 └──────┬──────┘
                        │
              ┌─────────┴─────────┐
              │                   │
              ▼                   ▼
        Word Pipeline         PDF Pipeline
              │                   │
          Pandoc DOCX       Pandoc → Typst
              │                   │
              ▼                   ▼
            DOCX                 PDF
```

该架构是本项目必须保持的核心边界：

**GUI 不负责转换；转换服务不负责 UI；Word 不依赖 PDF；PDF 不依赖 Word；样式不直接写死在界面；所有第三方引擎都由资源层统一管理。**
